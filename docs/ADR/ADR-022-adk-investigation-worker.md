# ADR-022: End-to-End AI Investigation MVP — Google ADK, Asynchronous Celery Worker, Bounded Tool Gateway, and Deterministic Evidence Validation

- **Status:** ACCEPTED — VERIFIED
- **Date:** 2026-10-10
- **Governing rules:** `docs/AGENTS_DECISION_LOG_RULES.md`, `AEGISOPS_MASTER_IMPLEMENTATION_PLAN.md` Phase 2.
- **Related decisions:** ADR-001, ADR-002, ADR-004, ADR-005, ADR-006, ADR-015, ADR-018, ADR-021, DEC-251–DEC-260.

## Context and Problem Statement

Phase 1 established real application telemetry ingestion, Prometheus alerting, Alertmanager webhook delivery, and PostgreSQL incident persistence. However, diagnosing incidents manually requires operators to triage logs and metrics. Phase 2 requires:
1. An automated, asynchronous investigation engine triggered on incident dispatch.
2. A single-agent Google ADK (v2.11.0) architecture capable of investigating incidents using real telemetry.
3. A strictly bounded, read-only tool gateway querying live Prometheus and Loki without prompt injection or data leakage vulnerabilities.
4. Pre-export redaction of sensitive credentials, tokens, and secrets in telemetry payloads and evidence.
5. Deterministic evidence citation validation ensuring that all agent hypotheses cite strictly persisted evidence IDs generated by the tool gateway during that specific run.
6. Honest `INCONCLUSIVE` diagnosis when telemetry is insufficient, preventing hallucinations.
7. An interactive Next.js dashboard providing operators full visibility into investigation lifecycle, hypotheses, tool audit trails, and supporting evidence.

## Decision

1. **Asynchronous Task Architecture:**
   - Celery worker connected to Redis (`redis://redis:6379/0`) executing durable investigation tasks (`investigate_incident_task`).
   - Concurrency guard ensuring only one active investigation runs per incident episode.
   - Investigation lifecycle states: `QUEUED` -> `COLLECTING_CONTEXT` -> `INVESTIGATING` -> `VALIDATING` -> `COMPLETE` / `INCONCLUSIVE` / `FAILED`.

2. **Single-Agent Google ADK Framework:**
   - Single-agent topology using Google ADK `Agent` and `Runner.run_async` with pinned version 2.11.0.
   - Decoupled `OfflineInvestigationModel` generating deterministic tool calls and hypotheses for reliable automated testing, alongside Gemini and Groq API adapters.
   - Single-agent design prevents swarm complexity and keeps token consumption bounded.

3. **Bounded Read-Only Tool Gateway:**
   - `ReadOnlyToolGateway` restricts agent actions to three read-only tools:
     - `get_incident_snapshot(incident_id)`: returns structured incident alert metadata.
     - `query_service_metrics(service_name, metric_name, duration)`: queries live Prometheus instance.
     - `search_service_logs(service_name, query, limit)`: queries live Loki log streams.
   - Hard execution budget capped at 12 calls per investigation; exceeding calls raises `BudgetExceededError`.
   - Payload byte caps (32KB max per tool response).
   - Read-only parameterized queries: no raw SQL, arbitrary PromQL, or shell access.

4. **Sensitive Data Redaction:**
   - Synchronous pre-export regex filtering in `agents/incident_investigator/tools/redaction.py`.
   - Masks Bearer tokens, Basic authorization, private keys, connection strings, and passwords into `[REDACTED_SECRET]` before tool responses return to the agent or persist into PostgreSQL.

5. **PostgreSQL Evidence Persistence & Provenance:**
   - Alembic migration `0003_investigations.py` establishes tables: `investigation_runs`, `tool_executions`, `evidence_items`, and `hypotheses`.
   - Tool outputs generate immutable evidence items with deterministic prefixes (`ev_alert_...`, `ev_metric_...`, `ev_log_...`) stored in `evidence_items`.
   - Tool audit logs are captured in `tool_executions` with execution durations, arguments, and success status.

6. **Deterministic Evidence Citation Validation:**
   - Post-investigation validation function `validate_evidence` verifies all hypothesis citations.
   - Citations must match real evidence items persisted in PostgreSQL for that specific investigation run.
   - Any hallucinated or cross-run evidence IDs trigger immediate rejection, downgrading the diagnosis to `INCONCLUSIVE` with an audit error explaining the citation violation.

7. **Honest Inconclusive Diagnosis:**
   - When telemetry returns 0 errors or metrics are normal, the agent produces an `INCONCLUSIVE` diagnosis with low confidence, documenting missing telemetry rather than hallucinating root causes.

8. **Interactive Next.js Dashboard:**
   - Component `InvestigationPanel` renders investigation status, hypotheses with confidence tags, supporting evidence chips, inconclusive explanation banners, evidence explorer, and tool execution audit timeline.
   - Auto-polls every 2s during in-progress states (`QUEUED`, `INVESTIGATING`, `VALIDATING`).

## Alternatives Considered and Rejected

1. **Synchronous In-Process FastAPI Execution:** Rejected. Investigations take multiple seconds and multiple tool iterations. Running them within FastAPI request threads blocks worker processes and causes client timeouts.
2. **Multi-Agent Hierarchical Swarm:** Rejected as premature over-engineering (violates ponytail rule). A single well-bounded investigator achieves all Phase 2 requirements with lower latency, lower cost, and zero coordination failure modes.
3. **Unbounded Agent PromQL / LogQL / Shell Access:** Rejected. Exposing raw query interfaces to an LLM creates prompt injection vulnerabilities and risks DoS attacks on telemetry backends.
4. **Client-Side or LLM-Judged Citation Verification:** Rejected. LLM outputs cannot judge their own citations. Verification must be deterministic backend code querying database foreign keys.
5. **Synthetic AI Outputs Without Real Telemetry:** Rejected. Portfolio integrity requires real telemetry querying Prometheus and Loki backends with verified diagnostic output.

## Phase 2 Corrective Fix Amendment (2026-10-11)

Following Phase 2 audit, two critical defects were resolved:
1. **Root-Cause Causal Grounding (DEC-261, DEC-262):** S01 (`S01_CHECKOUT_500`) was previously misdiagnosed as "Database Connection Pool Exhaustion in /checkout" with 0.95 confidence because generic HTTP 500 error counters were accepted as proof of DB pool exhaustion. The pipeline was amended to distinguish citation integrity from causal claim support: generic 500 counters cannot prove DB pool contention without database diagnostic telemetry; explicit contradictions (e.g. gateway timeout logs vs claimed DB exhaustion) are rejected; S01 diagnoses controlled application exception / payment processing gateway timeout on `/checkout` (`CHECKOUT_GATEWAY_TIMEOUT`).
2. **Explicit Qualitative Confidence Contract (DEC-263):** Public contract standardized strictly to `low | medium | high` with explicit `unverified_assumptions`. Legacy database floats are safely coerced by API validators without data corruption.
3. **Explicit Execution Mode & Silent Fallback Prohibition (DEC-264):** Introduced `AEGISOPS_AGENT_MODE=offline|live`. Offline model runs deterministically for CI; live mode calls Google GenAI directly. If credentials fail or quota is exhausted (429), the run fails cleanly without silent fallback to the offline model.
4. **Structured Verification Decoupling (DEC-265):** Restructured E2E test into 4 independent gates (Infrastructure, Diagnostic Correctness, Model Authenticity, Security) with 28/28 checks passing.
